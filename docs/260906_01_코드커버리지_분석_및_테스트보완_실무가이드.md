## 1. 개요: 커버리지의 본질과 "100%의 함정"

### 1.1 왜 코드 커버리지를 측정하는가?
단위 테스트가 121개 모두 통과(`121 PASSED`)했더라도, 그것이 **"애플리케이션의 모든 비즈니스 로직과 예외 상황이 안전하게 점검되었다"**는 것을 의미하지는 않습니다.

* **단위테스트 결과 보고서**: "작성된 테스트 케이스가 기대한 대로 동작하는가?" (테스트 통과 여부)
* **코드 커버리지 보고서**: "작성된 테스트들이 실제 프로덕션 코드의 **어느 경로(라인/분기)까지 실행시켰고, 어디를 놓치고 있는가?**" (테스트 빈틈 탐지)

---

### 1.2 커버리지 100%를 고집할 필요가 없는 이유
실무에서 **"라인 커버리지 100%"**를 목표로 삼으면 다음과 같은 부작용이 발생합니다:

1. **무의미한 테스트 양산**: 단순 Getter/Setter, 단순 생성자, `Exception` 클래스 선언부 등을 억지로 호출하는 가치 낮은 테스트에 개발 공수가 낭비됩니다.
2. **테스트 취약성 증가**: 내부 구현이 조금만 바뀌어도 깨지는 결합도 높은 테스트가 늘어납니다.
3. **검증(Assertion) 없는 커버리지 착시**: 단순히 코드를 실행만 시키고 정작 `assert` 검증을 하지 않아도 커버리지 수치는 올라갑니다.

> 💡 **핵심 원칙**:  
> 커버리지는 **"점수(Score)"**가 아니라 **"사각지대(Blind Spot) 탐색용 레이더"**입니다.  
> 커버리지 80% 내외를 유지하면서, **"놓치면 장애로 이어지는 핵심 분기와 엣지 케이스"**가 포함되어 있는지를 판단하는 잣대로 활용해야 합니다.

## 2. JaCoCo 지표 해석 및 보고서 수치 확인법

[코드커버리지보고서.md](file:///d:/dev/workspace/git.jkoogihw/batchLogAnalyze/report/코드커버리지보고서.md)와 HTML 리포트에서 제공하는 6대 지표의 의미와 해석 기준입니다.

```
+------------------------------------------------------------------------------------+
|                                 JaCoCo 6대 핵심 지표                               |
+-------------------+----------------------------------------------------------------+
| 1. Line (라인)     | 실행 가능한 전체 코드 라인 중 테스트가 한 번이라도 실행한 비율  |
| 2. Branch (분기)   | if, switch, 삼항 연산자 등 조건식의 참/거짓 양 갈래 실행 비율  |
| 3. Instruction     | 자바 바이트코드 명령어 수준의 실행 비율 (가장 세밀한 단위)       |
| 4. Method (메서드) | 클래스 내 전체 메서드 중 1회 이상 호출된 메서드 비율           |
| 5. Complexity      | 순환 복잡도(Cyclomatic Complexity) 기반의 실행 경로 점검률     |
| 6. Class (클래스)  | 프로젝트 내 전체 클래스 중 1개 이상의 메서드가 실행된 클래스 비율|
+-------------------+----------------------------------------------------------------+
```

### 2.1 지표별 해석 및 실무 목표 권장치

| 지표 | 현재 수치 | 권장 목표 | 실무 의미 및 해석 가이드 |
| :--- | :---: | :---: | :--- |
| **Line Coverage** | **80.1%** | `75% ~ 85%` | • 전체 코드의 대다수가 최소 1회 이상 실행됨<br>• 80% 이상이면 핵심 흐름(Happy Path)은 검증된 상태 |
| **Branch Coverage** | **57.5%** | `60% ~ 75%` | • **가장 중요한 품질 지표**<br>• `if` 조건문의 `false` 분기나 `null` 처리, 예외 발생 경로가 누락되어 있음을 시사함 |
| **Method Coverage** | **73.2%** | `70% ~ 80%` | • 미사용 레거시 메서드나 오버로딩된 편의 메서드의 테스트 여부 확인 |
| **Class Coverage** | **90.9%** | `85% ~ 95%` | • 55개 클래스 중 50개 클래스가 테스트에 참여함 (예외 클래스 제외 시 사실상 전수 참여) |

---

### 2.2 HTML 보고서 색상 식별법

Eclipse 내장 커버리지 또는 `build/reports/jacoco/test/html/index.html`을 열었을 때 코드 라인별로 3가지 색상이 표시됩니다:

* 🟩 **녹색 (Covered)**: 테스트가 실행되어 정상 점검된 라인입니다.
* 🟨 **노란색 (Partially Covered)**: 해당 라인에 조건문(`if`, `&&`, `||`)이 있으나, **일부 분기만 실행**된 경우입니다. (예: `if (a != null)`에서 `true`만 테스트되고 `false(null)` 케이스는 미테스트)
* 🟥 **빨간색 (Missed)**: 테스트 실행 중에 단 한 번도 진입하지 않은 **완전 미점검 라인**입니다.

## 3. 커버리지 지표를 통한 테스트 보완 판단 기준

커버리지 보고서를 볼 때 **"어떤 테스트를 추가하고, 어떤 것은 지나쳐도 되는지"**를 결정하는 3단계 필터링 기준입니다.

```
                      [ 커버리지 분석 3단계 의사결정 트리 ]
                                        │
                         [커버리지가 낮거나 분기 누락 발생]
                                        │
                  ┌─────────────────────┴─────────────────────┐
                  ▼                                           ▼
         [비즈니스 로직인가?]                        [보일러플레이트/설정인가?]
                  │                                           │
         ┌────────┴────────┐                         ┌────────┴────────┐
         ▼                 ▼                         ▼                 ▼
   [결과에 영향 큼]   [방어적 null체크]             [사용자 예외 클래스] [단순 toString/Getter]
         │                 │                         │                 │
    ★ 즉시 보완         ★ 선택적 보완                 ☆ 테스트 불필요      ☆ 테스트 불필요
  (오류 판정 누락)   (시스템 안정성 강화)          (검증 실익 없음)   (유지보수 비용만 증가)
```

### 3.1 필수 보완 대상 (Must-Have)
* **상태 전이(State Transition) 로직**: `CheckResult`의 PASS -> FAIL -> HOLIDAY 전환
* **조건 판정(Rule Evaluator)**: `EQUALS_0`, `EQUALS_N`, `ERROR_IF_PRESENT`, `ROLLBACK_ZERO` 등 배치 성공/실패를 결정짓는 분기
* **문자열/수치 파싱 경계값**: 콤마 포함 숫자(`1,234`), 단위 포함(`100건`), 정규식 와일드카드 매칭

### 3.2 선택적 보완 대상 (Nice-to-Have)
* **방어적 파라미터 검증**: `logFiles == null`, `policy == null` 등 호출자가 `null`을 넘겼을 때 안전하게 `null` 또는 빈 목록을 반환하는지 검증
* **파일명 포맷 엣지케이스**: 확장자가 없는 파일명, 예상치 못한 구분자가 포함된 로그 라인

### 3.3 보완 불필요 대상 (Skip / Low-Value)
* **단순 도메인 예외 클래스 (`com.batch.exception.*`)**: `super(message)`만 호출하는 단순 예외는 커버리지가 0%여도 품질에 영향 없음
* **단순 DTO 빌더/toString**: 필드 매핑만 담당하는 보일러플레이트 코드
* **`main(String[] args)` System.exit 분기**: 통합 실행 레벨에서 점검되므로 개별 CLI 옵션 파싱 단위테스트로 대체

## 4. 실전 코드 기반의 테스트 보완 케이스 스터디

현재 프로젝트의 실제 소스 코드를 바탕으로 **어디서 분기가 누락되었고, 어떤 테스트를 추가해야 하는지** 구체적인 코드 예시입니다.

### 💡 사례 1: `LogFileLocator` — 방어 로직 및 확장자 엣지케이스

#### 📌 대상 코드 ([LogFileLocator.java](file:///d:/dev/workspace/git.jkoogihw/batchLogAnalyze/src/main/java/com/batch/analyzer/LogFileLocator.java#L25-L62))
```java
public File locate(File[] logFiles, JobPolicy policy) {
    if (logFiles == null || policy == null) return null; // [분기 1: null 케이스]

    // 1. 표준 접두사 매칭 우선
    if (policy.filePrefix != null && !policy.filePrefix.isEmpty()) { ... }

    // 2. 미변경 원본 파일명 패턴 매칭
    if (policy.rawPattern != null && !policy.rawPattern.isEmpty()) {
        for (File f : logFiles) {
            String name = f.getName();
            if (policy.rawPattern.contains("%")) {
                String[] parts = policy.rawPattern.split("%");
                String basePattern = parts[0];
                String suffix = parts.length > 1 ? parts[1] : ""; // [분기 2: suffix 부재]

                if (name.contains(basePattern)) {
                    String nameWithoutExt = name.contains(".") ? 
                            name.substring(0, name.lastIndexOf('.')) : name; // [분기 3: 확장자 없음]
                    if (nameWithoutExt.endsWith(suffix)) {
                        return f;
                    }
                }
            }
            ...
        }
    }
    return null;
}
```

#### 🔍 커버리지 누락 원인
1. `logFiles == null` 또는 `policy == null`이 전달되었을 때 조기 리턴되는 경로 미테스트
2. 와일드카드 패턴에서 `suffix`가 없는 경우 (`parts.length <= 1`)
3. 로그 파일명에 확장자(`.log`)가 없는 순수 파일명인 경우

#### ✅ 보완 테스트 코드 예시 (`LogFileLocatorTest.java`)
```java
@Test
@DisplayName("방어 로직: logFiles 또는 policy가 null일 때 안전하게 null 반환")
void locate_NullInputs_ReturnsNull() {
    LogFileLocator locator = new LogFileLocator();
    JobPolicy policy = JobPolicy.builder("01", "TestJob").filePrefix("01_").build();

    assertNull(locator.locate(null, policy));
    assertNull(locator.locate(new File[]{}, null));
}

@Test
@DisplayName("엣지 케이스: 확장자가 없는 파일명 및 rawPattern 와일드카드 매칭 검증")
void locate_FileNameWithoutExtension_MatchesCorrectly() {
    LogFileLocator locator = new LogFileLocator();
    JobPolicy policy = JobPolicy.builder("11", "Job11")
            .rawPattern("_11268_%16_1")
            .build();

    // 확장자가 없는 파일: "batch_11268_20260906_16_1"
    File fileWithoutExt = new File("batch_11268_20260906_16_1");
    File[] files = new File[]{ fileWithoutExt };

    File matched = locator.locate(files, policy);
    assertNotNull(matched);
    assertEquals("batch_11268_20260906_16_1", matched.getName());
}
```

### 💡 사례 2: `DisplayRuleEvaluator` — 비정상 수치 파싱 및 조건별 실패 분기

#### 📌 대상 코드 ([DisplayRuleEvaluator.java](file:///d:/dev/workspace/git.jkoogihw/batchLogAnalyze/src/main/java/com/batch/analyzer/evaluator/DisplayRuleEvaluator.java#L43-L82))
```java
switch (condition) {
    case EQUALS_0:
        if (numValue != null) {
            passed = (numValue == 0);
            message = passed ? "정상 (0건)" : "오류 (" + extracted + ")";
        } else if (extracted == null) {
            passed = false;
            message = "값 미추출 (항목 미존재)";
        } else {
            // [누락 분기]: 값은 추출되었으나 숫자로 파싱되지 않는 비정상 텍스트 (예: "SUCCESS")
            passed = false;
            message = "수치 파싱 실패 (" + extracted + ")";
        }
        break;

    case ERROR_IF_PRESENT:
        if (extracted != null && !extracted.trim().isEmpty()) {
            if (numValue != null && numValue == 0) {
                passed = true;
                message = "정상 (0건)";
            } else {
                passed = false;
                message = "오류 발생 (" + extracted + ")";
            }
        } else {
            // [누락 분기]: Warning 키워드 자체가 로그에 전혀 나타나지 않는 경우
            passed = true;
            message = "정상 (미발생)";
        }
        break;
}
```

#### 🔍 커버리지 누락 원인
* `EQUALS_0` 룰에서 문자가 숫자가 아닌 경우(파싱 실패)에 대한 실패 처리 검증 누락
* `ERROR_IF_PRESENT`에서 키워드가 아예 없는 경우(`extracted == null`)의 정상(`passed = true`) 판정 검증 누락

#### ✅ 보완 테스트 코드 예시 (`DisplayRuleEvaluatorTest.java`)

```java
void evaluate_Equals0_NonNumericValue_FailsGracefully() {

    assertTrue(result.passed);
    assertEquals("정상 (미발생)", result.message);
}
```

### 💡 사례 3: `LogDateChecker` — 기준일 결정 Fallback 경로

#### 📌 대상 코드 ([LogDateChecker.java](file:///d:/dev/workspace/git.jkoogihw/batchLogAnalyze/src/main/java/com/batch/analyzer/LogDateChecker.java#L151-L182))
```java
public LocalDate resolveBaseDate(String folderName, File[] logFiles, LocalDate defaultDate) {
    // 1. 6자리/8자리 폴더명 파싱
    LocalDate fromFolder = parseDateFromFolderName(folderName);
    if (fromFolder != null) return fromFolder;

    // 2. 파일 헤더에서 날짜 탐색 (Fallback)
    LocalDate fromFiles = detectBaseDateFromFiles(logFiles);
    if (fromFiles != null) return fromFiles;

    // 3. 최종 Fallback: defaultDate 반환
    return defaultDate != null ? defaultDate : LocalDate.now();
}
```

#### 🔍 커버리지 누락 원인
* 폴더명도 날짜가 아니고, 로그 파일 헤더에도 타임스탬프가 없는 극단적 상황에서 `defaultDate`가 반환되는 최종 Fallback 분기 미테스트

## 5. 테스트 보완을 위한 실무 작업 가이드 & 체크리스트

### 5.1 패키지별 점검 우선순위 매트릭스

```
   중요도 (비즈니스 영향도)
     ▲
  高 │  [1순위: 핵심 도메인 & 엔진]        │  [2순위: 파이프라인 & 평가기]
     │  • com.batch.policy (97.8%)          │  • com.batch.analyzer.pipeline (87.9%)
     │  • com.batch.model (83.3%)           │  • com.batch.analyzer.evaluator (73.9%)
     │  ------------------------------------+-----------------------------------
     │  [3순위: 서비스 & 유틸리티]          │  [4순위: 설정 & 단순 예외 (보완 불필요)]
     │  • com.batch.service (78.6%)         │  • com.batch.config (47.1%)
  低 │  • com.batch.extract (88.7%)         │  • com.batch.exception (0.0%)
     └──────────────────────────────────────┴─────────────────────────────────►
```

## 6. 요약 및 결론

1. **커버리지 수치의 가치**:
   * 커버리지는 단순한 합격 점수가 아니라, **"우리가 미처 생각하지 못한 비즈니스 예외와 엣지 케이스가 어디에 숨어있는지"** 알려주는 최적의 나침반입니다.
2. **현재 프로젝트 상태**:
   * **라인 커버리지 80.1%**, **클래스 커버리지 90.9%**로 핵심 기능(Job 정책, 룰 평가, 파이프라인, 보고서 작성)은 매우 견고하게 테스트되고 있습니다.
3. **향후 보완 추천 방향**:
   * 라인 커버리지를 100%로 올리기 위해 불필요한 테스트를 늘리기보다는, **분기 커버리지(Branch Coverage, 현재 57.5%)**를 65~70% 수준으로 끌어올릴 수 있도록 **"비정상 포맷", "null 입력", "수치 파싱 실패"** 등의 엣지 케이스 단위 테스트를 점진적으로 추가하는 것을 권장합니다.
