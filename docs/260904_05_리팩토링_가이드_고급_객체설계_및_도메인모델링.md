## 1. 개요 및 학습 목표

초기 개발 단계에서는 빠른 기능 완성을 위해 **절차적 방식(Procedural Programming)**으로 코드를 작성하기 쉽습니다. 컨트롤러나 서비스 클래스가 데이터 객체(DTO/Model)의 내부 필드를 꺼내 직접 조건문을 돌리고 상태를 변경하는 방식입니다.

하지만 비즈니스 로직이 복잡해질수록 다음과 같은 문제에 직면합니다:
1. 같은 데이터 묶음(`String fullText, String[] lines`)이 여러 클래스로 복사되어 돌아다님
2. 메서드 인자가 5~6개 이상으로 늘어나 호출부가 지저분해지고 변경에 취약해짐
3. 새로운 검증/비즈니스 단계가 추가될 때마다 거대한 `if-else` 분기문이 계속 커짐 (OCP 위반)

본 가이드는 **배치 로그 분석 시스템(`batchLogAnalyze`)**의 실제 리팩토링 사례를 바탕으로, 초급 개발자가 실무 프로젝트(Spring Boot, 웹 API, 배치 등)에서 **객체 지향적인 클린 아키텍처로 점진적으로 코드를 전환하는 방법**을 상세하게 안내합니다.

## 2. 핵심 객체 지향 설계 개념 이해

### 2.1 일급 객체(First-Class Object) & 값 객체(Value Object)
- **원시값 집착(Primitive Obsession)**: 도메인의 고유한 개념을 단순 문자열(`String`), 숫자(`int`), 배열(`String[]`) 등 원시 타입으로만 표현하려는 안티패턴.
- **데이터 뭉치(Data Clump)**: 항상 함께 붙어 다니는 2개 이상의 변수들 (예: `fullText`와 `lines`, `startDate`와 `endDate`, `zipCode`와 `address`).
- **해결책**: 이들을 묶어 고유한 불변(Immutable) 객체로 승격시킵니다.
  ```java
  // ❌ Before: 항상 둘이 함께 다녀야 하고, 누군가 lines를 잘못 쪼개면 불일치 발생
  void process(String fullText, String[] lines);

  //  After: LogContent가 텍스트와 라인 데이터의 일관성을 스스로 보장하고 관련 행위를 제공
  void process(LogContent logContent);
  ```

### 2.2 매개변수 객체 (Parameter Object)
- **긴 매개변수 목록(Long Parameter List)**: 메서드 인자가 4~5개를 넘어가면 순서 혼동, 가독성 저하, 변경 시 광범위한 컴파일 에러가 발생합니다.
- **해결책**: 관련된 매개변수들을 하나의 **문맥(Context) 객체**로 묶습니다.
  - 신규 옵션(예: 타임아웃, 엄격 모드 등)이 추가되어도 기존 호출부의 메서드 시그니처를 깨뜨리지 않고 확장이 가능합니다 (OCP 달성).

### 2.3 풍부한 도메인 모델 (Rich Domain Model) & "Tell, Don't Ask" 원칙
- **무기력한 도메인 모델 (Anemic Domain Model)**: 데이터(Getter/Setter)만 있고 비즈니스 행위가 없는 껍데기 객체. 서비스나 유틸리티가 이 객체의 내부 필드를 직접 꺼내 판단하고 조작합니다.
- **풍부한 도메인 모델 (Rich Domain Model)**: 자신의 상태와 관련된 행위를 스스로 책임지는 객체.
- **Tell, Don't Ask (물어보지 말고 시켜라)**:
  ```java
  // ❌ Ask: 외부에 상태를 물어보고 외부에서 상태를 변경 (캡슐화 파괴)
  cr.fileFound = true;
  cr.fileName = targetFile.getName();
  cr.overallPassed = false;

  //  Tell: 객체에게 목적을 가진 행위를 명령 (내부 상태 전이 캡슐화)
  cr.attachLogFile(targetFile);
  cr.recordAnalysisFailure(throwable);
  ```

### 2.4 책임 연쇄 / 파이프라인 패턴 (Chain of Responsibility & Pipeline)
- 거대한 절차적 메서드 내부에서 `1단계 -> 2단계 -> 3단계 -> 4단계`를 순차적으로 실행하고 중첩 if문으로 흐름을 제어하는 대신, **각 단계를 독립된 `Step` 객체로 분리하여 파이프라인으로 연결**합니다.
- 각 단계는 독립적으로 테스트(단위 테스트)할 수 있고, 새로운 단계의 추가/삭제/순서 변경이 매우 쉬워집니다.

```mermaid
graph LR
    Ctx[JobAnalysisContext] --> S1[FileLocateStep]
    S1 -->|파일 발견| S2[DateCheckStep]
    S1 -->|미발견 (조기종료)| Res[CheckResult]
    S2 --> S3[HolidayCheckStep]
    S3 -->|비영업일 (조기종료)| Res
    S3 -->|영업일 (계속)| S4[RuleEvaluationStep]
    S4 --> Res
```

## 3. 리팩토링 전 코드 냄새 (Code Smell) 진단

리팩토링 전 `LogAnalyzer.java`의 실제 코드를 분석해 보겠습니다.

```java
// [리팩토링 전 LogAnalyzer.java 일부]
public CheckResult checkJobInstance(File workFolder, File[] logFiles, JobPolicy policy, String folderName, boolean skipDateCheck) {
    CheckResult cr = new CheckResult(policy);

    // 냄새 1: 파일 미발견 시 CheckResult의 내부 필드를 외부에서 직접 조작
    File targetFile = fileLocator.locate(logFiles, policy);
    if (targetFile == null) {
        cr.markAsFileNotFound(...);
        cr.addRuleResult(RuleResult.fail(...));
        return cr;
    }

    cr.fileFound = true;               // 냄새 2: Anemic Model (수동 상태 변경)
    cr.fileName = targetFile.getName();

    try {
        // 냄새 3: 오케스트레이터가 저수준 파일 I/O 및 Charset 파싱을 직접 수행
        String encodingName = Config.get("file.encoding", LogConstants.DEFAULT_ENCODING);
        Charset charset = Charset.forName(encodingName);
        String fullText = Files.readString(targetFile.toPath(), charset);
        String[] lines = fullText.split("\\r?\\n");

        // 냄새 4: Data Clump (fullText와 lines가 매번 짝을 지어 전달됨)
        RuleResult dateResult = dateChecker.checkDate(fullText, policy, folderName, logFiles, skipDateCheck);
        cr.addRuleResult(dateResult);

        // 냄새 5: 절차적 if 제어로직 강결합
        if (holidayChecker.checkAndApply(fullText, policy, cr)) {
            return cr;
        }

        if (policy != null && policy.rules != null) {
            for (Rule rule : policy.rules) {
                RuleResult rr = registry.evaluate(fullText, lines, rule);
                cr.addRuleResult(rr);
            }
        }
    } catch (Exception e) {
        // 냄새 6: 저수준 예외를 잡아서 실패 Result 객체를 수동으로 조립
        cr.overallPassed = false;
        RuleResult rr = new RuleResult();
        rr.ruleNo = LogConstants.RULE_NO_ERROR;
        rr.message = "오류 내용: " + e.getMessage();
        cr.addRuleResult(rr);
    }

    return cr;
}
```

### 🚩 진단된 주요 문제점 요약
1. **단일 책임 원칙(SRP) 위반**: `LogAnalyzer`가 파일 I/O, 텍스트 파싱, 예외 변환, 4단계 검증 흐름 제어를 모두 떠안고 있음.
2. **개방-폐쇄 원칙(OCP) 위반**: 새로운 검증 단계(예: 파일 크기 검사, 헤더 무결성 검사 등)가 생기면 `LogAnalyzer` 내부의 핵심 if-else 코드를 직접 뜯어고쳐야 함.
3. **원시값 집착 & 데이터 뭉치**: `fullText`와 `lines`라는 문자열 데이터가 계속 노출됨.
4. **긴 매개변수 목록**: 5개의 인자가 전달되어 가독성과 확장성이 떨어짐.

## 4. 단계별 점진적 전환 절차 (Step-by-Step Guide)

실무에서 대규모 리팩토링을 진행할 때 가장 중요한 것은 **"기존 기능이 단 1초도 깨지지 않는 안전성(Safety)"**입니다. 아래의 5단계를 거쳐 점진적으로 전환합니다.

### Step 1: 도메인 개념 식별 및 `LogContent` 일급 객체 추출

로그 텍스트와 줄(Lines) 데이터를 다루는 책임을 전담할 불변 Value Object `LogContent`를 만듭니다.

```java
package com.batch.model;

public class LogContent {
    private final File file;
    private final String fullText;
    private final List<String> lines;
    private final String[] linesArray; // 성능 최적화용 캐시

    private LogContent(File file, String fullText, List<String> lines) {
        this.file = file;
        this.fullText = fullText != null ? fullText : "";
        this.lines = lines != null ? Collections.unmodifiableList(new ArrayList<>(lines)) : Collections.emptyList();
        this.linesArray = this.lines.toArray(new String[0]);
    }

    // 팩토리 메서드 (I/O 및 인코딩 캡슐화)
    public static LogContent from(File file, Charset charset) throws IOException {
        String fullText = Files.readString(file.toPath(), charset);
        return new LogContent(file, fullText, parseLines(fullText));
    }

    // 테스트 지원용 팩토리 메서드
    public static LogContent of(String fullText) {
        return new LogContent(null, fullText, parseLines(fullText));
    }

    // 도메인 편의 행위 제공
    public boolean contains(String target) { return fullText.contains(target); }
    public boolean matches(Pattern pattern) { return pattern.matcher(fullText).find(); }
    public String getHeader(int maxLines) { ... }
}
```

> 💡 **주니어 팁**: `LogContent` 내부에서 `lines`를 `Collections.unmodifiableList()`로 감싸면 외부에서 리스트를 임의로 수정(`add`, `remove`)하여 도메인 불변식이 깨지는 문제를 원천 차단할 수 있습니다.

### Step 3: `CheckResult` 상태 전이 행위 캡슐화 ("Tell, Don't Ask")

`CheckResult`에 도메인 목적이 뚜렷한 메서드를 추가하여 외부에서 내부 boolean 필드를 직접 만지지 못하게 합니다.

```java
// CheckResult.java에 추가된 도메인 행위 메서드
public void attachLogFile(File file) {
    this.fileFound = true;
    this.fileName = file != null ? file.getName() : "";
}

public void recordAnalysisFailure(Throwable throwable) {
    String msg = throwable != null ? throwable.getMessage() : "원인 불명 오류";
    recordAnalysisFailure("파일 분석 중 오류 발생", "오류 내용: " + msg);
}

public void recordAnalysisFailure(String errorDescription, String errorMessage) {
    this.overallPassed = false;
    this.addRuleResult(RuleResult.fail(
            LogConstants.RULE_NO_ERROR,
            errorDescription != null ? errorDescription : "분석 오류",
            RuleType.UNKNOWN.getCode(),
            "ERROR",
            errorMessage != null ? errorMessage : "오류가 발생했습니다."
    ));
}
```

### Step 4: 절차적 실행 흐름을 `AnalysisPipeline`으로 구조화

각 검증 단계를 `AnalysisStep` 인터페이스 구현체로 분리합니다.

```java
// 1. 단계 인터페이스
@FunctionalInterface
public interface AnalysisStep {
    StepResult execute(StepExecutionContext context, CheckResult result) throws Exception;
}

// 2. 파이프라인 흐름 제어 (계속 진행 vs 조기 종료)
public class StepResult {
    public static StepResult next() { return new StepResult(Flow.CONTINUE, ""); }
    public static StepResult terminate(String reason) { return new StepResult(Flow.TERMINATE, reason); }
}

// 3. 개별 Step 구현체들
// - FileLocateStep (파일 탐색 & LogContent 로드)
// - DateCheckStep (로그 타임스탬프 일자 검증)
// - HolidayCheckStep (비영업일 감지 시 terminate)
// - RuleEvaluationStep (개별 규칙 평가)
```

**파이프라인 엔진 (`AnalysisPipeline.java`)**:
```java
public class AnalysisPipeline {
    private final List<AnalysisStep> steps;

    public CheckResult execute(JobAnalysisContext jobContext) {
        CheckResult result = new CheckResult(jobContext.getPolicy());
        StepExecutionContext execContext = new StepExecutionContext(jobContext);

        try {
            for (AnalysisStep step : steps) {
                StepResult stepResult = step.execute(execContext, result);
                if (stepResult != null && stepResult.isTerminated()) {
                    break; // 비영업일 예외 또는 파일 미발견 시 조기 종료
                }
            }
        } catch (Throwable t) {
            result.recordAnalysisFailure(t); // 도메인 메서드로 에러 캡슐화
        }

        return result;
    }
}
```

### Step 5: 어댑터/오버로딩을 통한 100% 하위 호환성 보장

기존 메서드를 삭제하지 않고, 내부적으로 신규 객체(`JobAnalysisContext`)로 변환하여 위임하도록 처리합니다.

```java
public class LogAnalyzer {
    private final AnalysisPipeline pipeline;

    //  [신규 권장 방식]
    public CheckResult checkJobInstance(JobAnalysisContext context) {
        return pipeline.execute(context);
    }

    // 🔄 [기존 레거시 호환 오버로딩]
    public CheckResult checkJobInstance(File workFolder, File[] logFiles, JobPolicy policy, String folderName, boolean skipDateCheck) {
        JobAnalysisContext context = JobAnalysisContext.of(workFolder, logFiles, policy, folderName, skipDateCheck);
        return checkJobInstance(context); // 신규 파이프라인으로 위임
    }
}
```

## 5. Before vs After 상세 코드 비교

### 📊 구조적 비교 요약

```
[Before: 절차적 강결합 모델]
Caller ───(5개 개별 인자 전달)───► LogAnalyzer (직접 파일I/O, Charset파싱, try-catch, if-else 제어)
                                      │
                                      ├──► dateChecker.checkDate(fullText, policy...)
                                      ├──► holidayChecker.checkAndApply(fullText, policy, cr)

[After: 파이프라인 & 도메인 캡슐화 모델]
Caller ───(JobAnalysisContext)───► LogAnalyzer ──► AnalysisPipeline
                                                         │
                                                         ├─► [1. FileLocateStep]     (LogContent 생성)
                                                         ├─► [2. DateCheckStep]      (일자 검증)
                                                         ├─► [3. HolidayCheckStep]   (비영업일 Short-circuit)
                                                         └─► [4. RuleEvaluationStep] (규칙 평가)
                                                                 │
                                                                 ▼
                                                            CheckResult (행위 캡슐화)
```

## 6. 장단점 및 트레이드오프 (Trade-off Analysis)

모든 아키텍처 패턴에는 비용(Cost)과 이점(Benefit)이 공존합니다. 실무에서는 언제 이 패턴을 도입해야 할지 판단할 수 있어야 합니다.

| 평가 항목 | 리팩토링 전 (절차적 방식) | 리팩토링 후 (고급 객체지향/파이프라인) | 트레이드오프 분석 및 실무 가이드 |
| :--- | :--- | :--- | :--- |
| **코드 가독성** | 한 메서드에 모든 흐름이 있어 짧을 때는 한눈에 보임 | 클래스와 파일 수가 늘어나지만, 각 클래스의 책임이 명확함 | 로직이 50줄을 넘어가거나 분기가 복잡해지면 파이프라인이 압도적으로 유리 |
| **확장성 (OCP)** | 새 검증 추가 시 기존 핵심 메서드를 수정해야 함 | 새로운 `AnalysisStep`을 만들어 파이프라인에 끼워 넣으면 끝 | 검증 단계가 수시로 추가/변경되는 비즈니스에 필수적 |
| **단위 테스트 용이성** | 전체 메서드를 통째로 실행해야 특정 단계 검증 가능 | `FileLocateStep`, `DateCheckStep` 등 단계별 독립 테스트 가능 | 테스트 작성 시간 단축 및 결함 추적성 대폭 향상 |
| **객체 생성 오버헤드** | `fullText`, `lines` 기본 자료구조만 사용 | `LogContent`, `JobAnalysisContext`, `StepResult` 등 객체 생성 | 현대 JVM에서는 단명 객체(Eden 영역) 수집 비용이 극히 미미하므로 무시 가능 |
| **학습 곡선** | 초급 개발자가 즉시 읽기 쉬움 | 파이프라인 구조와 인터페이스 추상화를 이해해야 함 | 팀 내 디자인 패턴 공유 및 표준화 문서(본 문서)가 필요함 |

> ⚠️ **주의: 오버엔지니어링(Over-Engineering) 경계하기**  
> 단순한 CRUD이거나 실행 단계가 1~2개뿐이고 앞으로 확장될 가능성이 없는 곳에 무조건 파이프라인 패턴을 적용하는 것은 불필요한 복잡성을 유발합니다.  
> **"단계가 3개 이상으로 늘어나고, 조건부 분기(조기 종료)가 발생하며, 단계가 계속 추가될 가능성이 있을 때"** 도입하는 것이 이상적입니다.

## 7. 실무 적용 체크리스트 및 응용 사례

다른 업무(웹 API, Spring Boot 서비스, 데이터 처리 배치 등)에서 유사한 문제를 만났을 때 다음 체크리스트를 활용하세요.

### 📋 실무 리팩토링 체크리스트
- [ ] 메서드의 인자가 4개 이상인가? ➡️ **`Parameter Object` (예: `UserRegistrationContext`) 도입 검토**
- [ ] 항상 같이 다니는 원시값(`startDate`, `endDate` 또는 `address`, `zipCode`)이 있는가? ➡️ **`Value Object` (예: `DateRange`, `Address`) 추출**
- [ ] 외부 서비스가 도메인 객체의 `getter`로 값을 꺼내서 `setter`로 수정하고 있는가? ➡️ **도메인 메서드로 행위 캡슐화 ("Tell, Don't Ask")**
- [ ] 하나의 메서드 안에 `step1() -> step2() -> step3()` if-else 분기문이 길게 늘어서 있는가? ➡️ **`Chain of Responsibility / Pipeline` 도입 검토**
- [ ] 기존 클라이언트의 코드를 깨뜨리지 않으면서 리팩토링할 수 있는가? ➡️ **기존 시그니처를 유지하고 내부에서 신규 객체로 감싸서 위임하는 어댑터 제공**

---

### 💡 실무 응용 예시: 회원가입 프로세스 파이프라인 적용

```java
// [일반적인 Spring 웹 서비스 예시]
public class UserRegistrationService {
    private final RegistrationPipeline pipeline;

    public RegistrationResult registerUser(UserRegistrationRequest request) {
        UserRegistrationContext context = UserRegistrationContext.from(request);
        return pipeline.execute(context);
    }
}

// 파이프라인에 등록된 Step 목록:
// 1. DuplicationCheckStep (아이디/이메일 중복 확인 -> 중복 시 조기 종료)
// 2. PasswordPolicyValidationStep (비밀번호 복잡도 검증)
// 3. PasswordEncryptionStep (BCrypt 암호화)
// 4. UserPersistenceStep (DB 저장)
// 5. WelcomeEmailDispatchStep (비동기 웰컴 메일 발송)
```

## 8. 결론

이번 리팩토링을 통해 `batchLogAnalyze` 시스템은:
1. **`LogContent`**를 통해 파일 I/O와 문자열 조작을 완벽히 격리시켰고,
2. **`JobAnalysisContext`**를 통해 깔끔하고 확장성 높은 인터페이스를 확보했으며,
3. **`AnalysisPipeline`**을 통해 검증 단계들의 결합도를 낮추고 완벽한 OCP를 달성했습니다.
4. 기존 호출부 및 104개의 단위 테스트 전체가 단 한 줄의 수정 없이 **100% 정상 작동(하위 호환성 100%)**합니다.
